# Steve Jobs Perspective

把乔布斯的表达方法当作一套**可检查的清单**，用来改造 B2B 工业设备的对外表达。不是模仿口吻，而是套用他的结构纪律与确定性机制。

## 何时用

- 整线方案提案 / PitchDeck 的叙事结构需要收紧
- 展会演讲、视频口播稿、客户会议开场需要更有说服力
- 现有文案充满 hedging（「我们觉得」「可能会」「大概」），需要改成确定性表达
- 需要把一个技术参数翻译成客户能感受的价值类比

## 何时不用

- 客户质量反馈、投诉回复、整改函 —— 用 `smt-customer-quality-feedback-response`，乔布斯语气在这里会显得傲慢
- 需要写精确参数、交期、保修条款的商务文件 —— 这些用 `smthelp-brand-voice` 的证据规则，不允许修辞覆盖事实

## 工作流程

### 1. 定位改造对象

确认要改的是**结构**、**语气**、还是**比喻**。三者混改容易改坏：

- 结构问题 → 走第 2 步
- 语气问题（hedging、被动语态、形容词堆砌）→ 走第 3 步
- 价值传达不清 → 走第 4 步

### 2. 套用三段式结构

乔布斯几乎所有发布都是三段。B2B 场景的对应映射：

| 乔布斯结构 | SMT 设备提案的对应 |
| --- | --- |
| 今天我们要发布一个产品 | 客户现状的瓶颈（用客户的产能/良率语言描述） |
| 它做三件事 | 方案的三条主线（不超过三条，多了就记不住） |
| 这就是为什么它重要 | 换算成 ROI / 换线时间 / 人力节省 |

**硬约束**：第三条主线之后不再新增。如果方案有五条卖点，合并成三条或拆成两个提案。

### 3. 清除 hedging

按 `03-expression-dna.md` 的 Certainty Patterns 逐句检查：

- 删除「我们觉得 / 可能会 / 应该可以 / 在一定程度上」
- 把被动语态改主动（「良率可以被提升」→「这条线把良率从 X 提到 Y」）
- 形容词换成数字或事实（「性能优异」→「CPH 从 A 到 B」）
- 不确定就不写，而不是写「可能」

**例外**：涉及交期、价格、认证、保修的表述必须保留合规措辞，不得为了语气而去掉限定条件。这一条优先于本 skill 的所有规则。

### 4. 用类比承载技术价值

从 `03-expression-dna.md` 的类比库里选一个结构（技术即魔法 / 自行车-for-the-mind / 木匠隐喻），替换成 SMT 场景的对应物。

示例结构（参数需按 `smthelp-brand-voice` 的术语表核对后才能填）：

> 一台贴片机的精度不是目的，它是让后面每一道工序都不需要返工的前提。

**硬约束**：类比只能解释已确认的参数，不能暗示不存在的能力。参数一律标注 `待确认` 直到有产品资料支撑。

### 5. 交付前自检

- [ ] 是否只有三条主线
- [ ] 有没有残留 hedging
- [ ] 每个形容词是否都能换成数字（换不掉的，删掉）
- [ ] 类比是否暗示了资料里没有的能力
- [ ] 交期 / 价格 / 保修类表述是否保留了限定条件
- [ ] 全程有没有使用「cheap」「best price」这类低价竞争词汇（Southern Machinery 禁用）

## 输出格式

给出**改写前后对照表**，而不是只给成品。Jason 需要看到改了什么、为什么改：

| 原句 | 问题 | 改写后 |
| --- | --- | --- |
| … | hedging / 形容词堆砌 / 结构松散 | … |

末尾附一句「如果是展会现场讲，建议在第 X 处停顿」。

## Do Not

- 模仿乔布斯的傲慢语气写客户回复或投诉处理
- 为了修辞效果夸大参数、良率、交期或客户案例
- 把本 skill 当作事实来源 —— 一切参数以 `smthelp-brand-voice` 的 SMT 术语表和产品资料为准
- 在合规敏感表述上去掉必要的限定词
