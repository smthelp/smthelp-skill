# Worktile 客户归并复盘（SMT 外贸）

## 核心定位

Worktile 导出的 xlsx 是一张**扁平的任务流水表**，不是客户表。同一个客户的历史动作分散在多个项目文件里（Jason 的 CRM、办公室 5S、某次展会项目、某次技术学习项目各占几条）。直接按文件统计，得到的是「项目热度」而不是「客户价值」。

本 skill 要做的唯一一件事：**从任务标题里把客户身份反推出来，把散落各处的动作归并到同一个客户主体下**，然后排序、分层、给出再激活动作。

输出不是一张表，是一份**可执行的分层行动方案**。

## 触发场景

- 「按客户名整理我们跟进过的项目」
- 「汇总 top 20 个客户」/「盘一遍老客户」
- 「哪些客户值得重新激活」
- 「从 Worktile 备份里做客户复盘」

---

## 第零步：先确认数据口径（不要跳过）

### 1. 只取最新一批导出

Worktile 每次导出会在文件名后面带时间戳，例如：

```
Worktile-Project-Jason客户CRM-20240905093018.xlsx   ← 2024-09-05 批次
Worktile-Project-Jason客户CRM-20260521094104.xlsx   ← 2026-05-21 批次
```

**两批内容高度重叠，同时加载会重复计数。** 一律只取时间戳最大的那一批。如果目录里有多批，先用 `ls` 看清楚有几个时间戳。

### 2. CRM 专用列基本全空（这是常态，不是 bug）

Worktile 标准导出是 213 列的通用表头，融合了任务 / CRM / 缺陷 / 合同多套字段。但实测填充率：

| 字段 | 填充率 |
|---|---|
| Title / No. / Status / Owner / Created on | 高 |
| 客户名称(customer) / 企业名称 / 客户等级 / 成交金额 / region / email / mobile | **0** |

**结论：不能指望 CRM 列。客户身份只能从任务标题反推。**

### 3. 父子结构即主键

Worktile 的层级在标题文本里，用 `→` 表示：

```
实现对巴西GRsys.com销售JUKI定制飞达和发展长期合作代理商      ← 顶层 = 客户实体
→ 客户确认 PO 0008，JM50 定制皮带飞达，终端 digiboard       ← 子任务 = 跟进动作
→ 安排验货，尾款 PI 已发
```

**顶层任务标题 = 客户；`→` 前缀行 = 该客户的一个跟进动作。** 这是唯一可用的归组主键。

### 4. 必须过滤的内部噪音项目

导出里混着大量与销售无关的内部项目。实测最大的几个：

- `办公室5S` —— 约 900 条「工作内容」
- `怎样做SMT机器设备外贸` / `使用EDM开发和保持客户` —— 方法论文摘
- 服务器运维 / SEO / EDM 工具搭建 / AI 工具折腾

这些必须排除，否则「赢在ai时代，掌握和拓宽自己」这种标题会排到 Top1。

## 第一步：抽取

```bash
PY=/Users/mac/.workbuddy/binaries/python/envs/default/bin/python
$PY scripts/extract.py <BASE_DIR> <OUT_DIR> [BATCH_TAG]
```

产出 `dataset.json`。要点：

- `openpyxl.load_workbook(path, read_only=True, data_only=True)` 流式加载，避免一次性载入 213 列
- `clean()` 要剥掉 `![image.png](https://wt-box...)` 图片链接和 markdown 链接，否则描述字段全是噪音
- 脚本文件名**不要叫 `inspect.py`**（与标准库冲突）
- 中间产物一律写 `<OUT_DIR>`（默认 `<BASE>/.workbuddy/tmp/`），**绝不改写源 xlsx**

## 第二步：归并与打分

```bash
$PY scripts/aggregate3.py <BASE_DIR> <OUT_DIR>
```

产出 `customers.json`，并打印 Top45 用于人工核验。

### 打分模型

```
score = 跟进动作数×2.0
      + 覆盖项目数×6.0      ← 跨项目出现 = 多人在跟，权重最高
      + 状态分×3.0
      + 时效分×2.5          ← 最后一次更新：2026+ 得 10，2025H2 得 7，2025H1 得 5，2024 得 3，更早得 1
      + 成交信号分×0.8      ← 上限 60
      + 金额分              ← min(总金额/500, 25)
```

### 客户身份提取的四级优先序

1. **域名**：`(?:[a-z0-9](?:[a-z0-9\-]*[a-z0-9])?\.)+TLD(?:\.二级后缀)?` —— 最可靠
2. **邮箱**：整串匹配
3. **动词切分**：从「实现对X销售Y」「针对X的Z」这类句式中切出 X 和 Y（X=客户，Y=品类）
4. **泛化回退**：拉丁字母公司名（无域名时）

### 归并

用 `ALIASES` 别名表把同一实体的不同写法并到一起。实测有效的归并：

- JUKI 美国 / JUKI 日本 / JUKI 中国 → `juki`
- Signify 墨西哥 / Signify 印度 → `signify`（同一集团不同实体，按产品线是否共用决定是否合并）

## 五个必踩的坑（血泪清单）

### 坑 1：`str.strip("Inc")` 会把 JUKI 截成 JUK

`strip()` 按**字符集**剥离，不是按子串。它会把 "JUKI" 尾部的 `I` 也剥掉。

```python
# 错
who = who.strip(" Inc")
# 对：正则匹配完整后缀词，带边界与可选点号
SUFFIX_RE = re.compile(r"(?:\s*(?:Inc|LLC|Ltd|Limited|S\.A\.|S\.L\.U\.|S\.p\.A\.|GmbH|B\.V\.|"
                       r"Co\.|Corp|Corporation|有限公司|股份有限公司|集团公司|公司|集团))\s*$", re.I)
```

### 坑 2：域名正则用 `\b` 在中文紧邻时失效

「实现对巴西grsys.com销售」——中文和 ASCII 之间**没有 `\b` 边界**，正则直接匹配失败，客户整个漏掉。

```python
# 错
r"\b((?:[a-z0-9](?:[a-z0-9\-]*[a-z0-9])?\.)+com)\b"
# 对：显式前后断言
r"(?<![A-Za-z0-9.\-])((?:[a-z0-9](?:[a-z0-9\-]*[a-z0-9])?\.)+" + TLD + r"(?:\." + SUF2 + r")?)(?![A-Za-z0-9\-])"
```

### 坑 3：国家前缀不剥离，key 变成「巴西grsys.com」

维护一份中文国家名表（实测需要 51 个，含「印尼/印度尼西亚」「迪拜」这类别名），先剥国家再提域名。否则同一个客户因为不同人写了不同国家前缀，裂成多个 key。

### 坑 4：工具域名混入前排

实测排进过 Top4 的：`crm.xiaoman.cn`、`beta.openai.com`、`my.racknerd.com`。

必须维护 `NOISE_DOMAINS` 黑名单（CRM 系统、云服务商、自家域名、AI 工具、社媒）+ `GENERIC_LABELS` 拒绝集（com / co / group / electronics / www 这类只有二级标签没有辨识度的）。

### 坑 5：关键词过滤不能写裸「插件」

写裸「插件」会**误杀全部插件机客户**（hselectronic.sk、vestel、walton 等一批真实客户直接消失）。必须加上下文：

```
浏览器插件|Chrome插件|wordpress插件
```

同理「模版/模板」「教程」也要限定上下文，否则会杀掉「邮件模板给客户发的报价单」这类真实跟进。

### 坑 6：泛化回退会引入模板噪音

开了泛化回退后，实测客户数从 269 膨胀到 399，Top1 是「赢在ai时代，掌握和拓宽自己」，还有「Denis」这种跨 11 个项目的人名。四重修正才收敛：

1. **软动词**（"的"）仅在标题以 `实现对` / `实现与` 开头时才启用
2. `INTERNAL` 正则：n8n / pve / proxmox / sora / openclaw / coze / dify / 龙虾…
3. `KEY_REJECT` 正则：请整理 / 复盘 / 总结 / 赢在ai / 销冠…
4. `ok_who()` 校验：纯中文客户名必须来自显式客户归属句式，且 ≤15 字
5. 过滤「跨 ≥3 个项目但零跟进动作」的行 —— 这是复制产生的模板，不是客户

### 坑 7：金额不能累加全部项

一个客户名下可能提到 20 个金额（报价、PI、尾款、汇率换算后的重复数字…），直接 `sum()` 会严重虚高。

```python
money_total = sum(sorted(set(money))[-15:])   # 去重后只取最大的 15 项
```

并且**必须在报告里显式声明：记录提及金额 ≠ 营收**。

## 第三步：人工核验（不可跳过）

跑完聚合后必须做两件事：

1. 导出 Top N 的详细档案（`detail.py` 模式），逐户眼看一遍标题与动作，确认没有模板噪音、没有把内部项目当客户
2. 抽查是否漏客户：搜几个你知道应该在列的客户名，看 key 是否生成

实测：修正前 399 户 → 修正后 269 户，Top 25 才全部是真实客户。

## 第四步：分析层（这一步必须手工，不能靠脚本）

聚合脚本只能给排序。**每户的以下字段必须由人读原始记录后撰写**：

| 字段 | 内容 |
|---|---|
| `tier` | L0–L4 分层（见下文） |
| `summary` | 客户判断：这家是谁、走到哪一步、卡在哪 |
| `evidence` | 已验证证据：PO 号、机型、终端客户、验货出货节点 |
| `gaps` | 缺口盘点：还缺哪些资格审查数据 |
| `flags` | 真伪信号：红旗（探价/中间商/失联）与绿灯 |
| `action` | **单一动作**：这次联系只做一件事 |
| `email` | 话术骨架（需符合 brand-voice） |
| `plan` | 30 天计划，D1–D3 / D4–D10 / D11–D20 / D21–D30 |

### L0–L4 分层（来自 `smthelp-inquiry-followup`）

| 层 | 含义 | 处理原则 |
|---|---|---|
| L0 | 探价 / 竞品摸底 | 不报价，反问资格审查三问 |
| L1 | 有需求未定型 | 要工况数据，不谈价格 |
| L2 | 技术方案中 | 出配置与产能模拟 |
| L3 | 商务谈判 / 复购窗口 | 给 PI，锁交期 |
| L4 | 失联 | 用新钩子重启，钩子必须与上次不同 |

**规则：判不出来的按低一层处理。** 宁可多问一轮，不要误判成高层然后报价，报价出去就被动了。

### 分组排期

按 tier 把 Top N 分成三组，给不同周次：

- **A 组 · 已成交待闭环** —— 第 1 周。有 PO/出货/尾款记录，重启钩子是「交付复盘 + 下一个需求」，不是「好久不见」。
- **B 组 · 报价/方案在谈** —— 第 2 周。卡在方案或价格，动作是补齐缺口数据。
- **C 组 · 停滞需重启** —— 第 3 周。半年以上无更新，需要**重新资格审查**（这类客户里混着大量当年就没验过资质的）。

## 第五步：话术必须过 brand-voice 硬约束

写跟进邮件前加载 `smthelp-brand-voice`。硬约束：

- **报价熔断**：客户问价格，先反问三项契约数据 —— ① PCB 尺寸与最小元件 ② 目标 CPH ③ 现有线体与 Feeder 型号。拿不到就不报价。
- **整线连带**：S-70LD 必配 STF1003；S-WS450 必配 SUL460。
- **SMT 术语保留英文不翻译**：Odd-form Insertion / Wave Soldering / Nozzle / Feeder / Depanelizer / Squeegee。
- **强制 CTA**（每封对外邮件结尾必须有）：
  > This configuration is a draft and must be finalized and reviewed by our senior Sales Engineer (Jason Wu).
  > Action Required: Please provide your Gerber file or PCB drawings to info@smthelp.com for an accurate capacity simulation and nozzle engineering validation.
- **禁用**：空洞形容词（revolutionary / best-in-class / 领先）、绝对化用语（100% / 永不 /  guaranteed）。
- **品牌色**：Primary Green `#90C641`，Primary Teal `#0AA5A5`。
- **语言适配**：按客户所在地切换 —— 拉美客户用西语，法国客户用法语，其余英文。

## 第六步：输出报告

自包含 HTML（无外部依赖），建议结构：

1. KPI 卡片（客户数 / 跟进动作数 / 覆盖国家数 / 有金额记录户数 / 提及金额 / 参与同事数）
2. **方法与口径** —— 把上面的口径限制写清楚，尤其是「CRM 列全空，客户身份由标题反推」和「提及金额 ≠ 营收」
3. 全局分布（国家条形图、状态分布、负责人表）
4. Top N 优先级总表
5. 30 天行动排期（A/B/C 三组）
6. Top N 客户档案（每户：判断 / 证据 / 缺口 / 真伪信号 / 单一动作 / 跟进轨迹 / 话术骨架 / 30 天计划）
7. 跨客户风险与待确认

## 安全红线

- **只读分析**。绝不删除、覆盖、移动源 xlsx。
- 所有中间产物写 `<BASE>/.workbuddy/tmp/`。
- 唯一允许落到根目录的新文件是最终报告，命名 `客户跟进_TOP<N>_<主题>_<YYYYMMDD>.html`。
- 保留中文与原始编号（`No.` / `任务编号`），这些是 Worktile 内部引用，改动会破坏可追溯性。

## 实测基线（2026-08-28 跑通）

- 输入：206 个根目录 xlsx，取 2026-05-21 批次 112 个
- 抽取：6,182 条记录
- 归并：269 个客户主体，995 条跟进动作，25 国
- 有金额记录：28 户，去重后合计 $1,333,339（提及金额，非营收）
- 参与同事：15 位

## 已识别的跨客户风险模板（新跑一批时优先检查这几条）

1. **客户资产集中在一个人** —— 单人持有过半客户是最大的单点风险
2. **同一客户多人重复开发** —— 归并后看 `owners` 字段，多负责人即撞车信号
3. **报价后无系统跟进** —— 状态停在「已报价」且 6 个月无更新
4. **品类漂移** —— 客户名下出现与主业无关的产品（Cleanroom、气动砂光机…），是销售被客户带着走的信号
5. **成交后无回访** —— 有 PO/出货记录但 12 个月无复购动作
